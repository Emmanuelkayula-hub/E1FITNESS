# E1FITNESS

A local-first workout, nutrition and progress tracker. Vanilla JS, no backend,
no account, no cloud sync — your data lives on your device (`localStorage`,
mirrored into native app storage on iOS/Android via Capacitor's WebView).

## Project structure

```
src/                     the actual application (the source of truth)
  index.html             entry point
  css/
    app.css              all app styles (unchanged from the original single-file build)
    fonts.css            @font-face rules pointing at the bundled font files
  js/
    app.js                the entire application logic — DB, rendering, every
                          screen, the rest timer, etc. Byte-for-byte identical
                          to the script block from the original single-file
                          e1fitness.html, except for one small addition: the
                          Settings → Export handler now branches to a native
                          Share Sheet when running inside Capacitor (see below).
    native-bridge.js      Capacitor-only glue (status bar, splash screen, native
                          export). A no-op on the desktop/browser build.
  assets/
    fonts/                self-hosted Oswald / Figtree / IBM Plex Mono (woff2)
    icon/                 app icon source used for the web <link rel="icon">
    icons/                generated PWA-style icon set

ios/                      native Xcode project (generated by `npx cap add ios`)
android/                  native Android Studio/Gradle project (generated by `npx cap add android`)
resources/                1024x1024 icon.png and 2732x2732 splash.png used by
                          `npx capacitor-assets generate` to produce every
                          platform-specific icon/splash size in ios/ and android/
capacitor.config.json     Capacitor configuration (app id, web dir, plugins)
package.json              npm scripts + Capacitor dependencies
```

`ios/` and `android/` are real native projects, not stubs — they were generated
by the official Capacitor CLI and contain the web app copied into their
respective platform asset folders (`ios/App/App/public`,
`android/app/src/main/assets/public`). That copy is regenerated by `npx cap
sync` and is gitignored; **`src/` is the only thing you should ever edit.**

## Why the source was split this way

The original app was one 4,900-line HTML file. It's now three files
(`index.html` / `app.css` / `app.js`) with **no logic changes** — this was a
mechanical extraction (verified with a byte-for-byte diff against the
original), done so the code has proper file boundaries without risking a
rewrite of a working, already-iPhone-tested application. `native-bridge.js`
is new and entirely additive.

## Build / run workflow

```bash
# 1. install dependencies
npm install

# 2. after any change under src/, sync it into both native projects
npm run sync
#    (equivalent to: npx cap sync)

# 3a. open the iOS project in Xcode (requires a Mac + Xcode + CocoaPods)
npm run open:ios
#    first run: cd ios/App && pod install   (CocoaPods isn't available in
#    every environment, e.g. this project was scaffolded on Linux, where
#    `cap add ios` skips the pod install step automatically)

# 3b. open the Android project in Android Studio (requires the Android SDK)
npm run open:android

# Or run directly on a connected device/simulator once the platform tooling above is set up:
npm run run:ios
npm run run:android
```

### Web / desktop version

`src/index.html` is a normal static web page — open it directly in a browser,
or serve the `src/` folder with any static file server. No build step is
required for the web version; it never depends on Capacitor (`native-bridge.js`
checks `window.Capacitor` and does nothing if it's absent).

### Regenerating app icon / splash screen

`resources/icon.png` (1024×1024) and `resources/splash.png` (2732×2732) are
the source images. To regenerate every platform size after changing them:

```bash
npm run assets
npm run sync
```

## Data & storage

The app stores everything in `localStorage` under the key `e1fitness_db_v1`,
exactly as before. Capacitor's WebView (WKWebView on iOS, the system WebView
on Android) persists `localStorage` the same way a normal browser does, and
this was kept deliberately rather than migrated to a native SQLite/Preferences
store for this first mobile release — see the migration report for the
reasoning and the plan for validating this is durable enough on real devices.

Settings → Data → Export/Import continues to produce/read the same JSON
backup format. On native platforms, Export now hands the file to the native
Share Sheet (there's no browser download manager inside a bare WebView to
catch a plain `<a download>` click); on the web it still downloads a file
exactly as before.

## Deployment (GitHub Pages) & getting updates onto your phone

The web build (`src/`) is deployed to GitHub Pages by
`.github/workflows/deploy-pages.yml`, which runs automatically on every push
to `claude/e1fitness-redesign-m1nzsz` (one-time setup: repo Settings → Pages
→ Source → "GitHub Actions" — already done). There is no separate build
step to run locally; the workflow deploys `src/` as-is.

**Standard change workflow:**
1. Changes are made locally under `src/` and tested (syntax check, the
   Playwright regression pass, a mobile-viewport check) *before* anything is
   pushed.
2. You get a summary of what changed and a chance to review it.
3. Only once you approve does a push go to this branch.
4. The Actions workflow above picks it up automatically and deploys within
   about a minute — no manual redeploy step.

**Making sure your phone loads the new version, not a stale cached one:**
the app has no service worker (deliberately — see below), but plain browser
HTTP caching can still leave Safari holding onto an old copy of `app.js`.
Two things handle this:
- Every deploy is stamped with the commit's short SHA. Each deploy's
  `index.html` references its JS/CSS with a `?v=<sha>` query string, so a
  new deploy is always a *new URL* to the browser — it can never be served
  from a stale cache under the same URL.
- `src/js/version-check.js` checks a small `version.json` (also stamped by
  the workflow) shortly after load and whenever the tab regains focus. If
  it doesn't match the version already running, it shows a toast with a
  **Refresh** button — tapping it does a normal page reload, which never
  touches `localStorage`, so your workouts/food logs/weight/settings are
  untouched.

**Why no service worker / full PWA setup:** the app didn't have one, and
adding one is exactly the kind of thing that *causes* "stuck on an old
version" bugs if the activation/update lifecycle isn't handled carefully.
The `?v=<sha>` + `version.json` approach above gets the same practical
result (reliably fresh code, no stale-cache trap) with far less to get
wrong. If true offline support (works with zero network at all, not just
"works because the browser already has it cached") becomes a priority,
that's a good candidate for a dedicated follow-up pass — see the migration
report's "next milestone" note.
